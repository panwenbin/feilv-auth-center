# feilv-auth-center

`feilv-auth-center` 是 `fei.lv` 工具矩阵的统一账户、授权、订阅与集成中心；**底层安全、密钥、证书与部分身份基础能力由 Vault 提供**。

它的目标不是一开始就做成一个大而全的 IAM 平台，也不是把 Vault 包成一个终端用户产品，而是优先解决 `fei.lv` 体系内多个工具和产品的共用问题：

- 统一用户账号
- 单点登录（SSO）流程编排
- API Key 元数据管理
- 订阅套餐与功能权限
- License / 激活码 / 私有部署授权
- 应用接入与子域名集成
- 控制台与商业化流程
- 密钥、签名、证书等安全能力与 Vault 集成

## 为什么要做这个项目

目前 `fei.lv` 正在通过 Web 小工具持续积累流量。随着工具数量增加，后续会自然遇到这些问题：

- 每个工具重复做登录和用户体系
- 无法统一管理免费版、Pro、Team 等套餐
- 无法为 API、私有部署和桌面/命令行工具提供统一授权能力
- 工具之间账号割裂，用户体验差
- 后期想做 SSO、组织、团队权限时成本很高
- 密钥、证书、签名逻辑如果自己重复实现，安全与维护成本高

`feilv-auth-center` 的定位就是用最小可行方式，把业务控制面抽出来，并把安全底层尽量建立在 Vault 之上。

## 与 Vault 的关系

### `feilv-auth-center` 负责什么

- 用户产品账户
- 应用注册与工具接入
- 套餐 / Feature / 订阅
- API Key 与 License 的业务模型
- SSO 流程与控制台体验
- 管理后台与商业化闭环

### Vault 负责什么

- Secrets 管理
- Transit 加密 / 签名 / HMAC
- PKI / 证书能力
- 机器身份与部分 auth method
- 安全审计基础

### 为什么这样分层

Vault 擅长认证方法、identity、policy、token、lease、transit、PKI 等安全基础能力，但它不是面向 `fei.lv` 最终用户的完整产品账户系统。Vault 支持多种 auth methods，认证后会生成 token 并赋予 policies；其 identity 模型可以将不同身份源整合为 entity/alias 表示。citeturn0search0turn0search1turn0search11

Vault 的 transit 引擎适合承担签名、校验、HMAC、加密等敏感操作；这样可以减少在业务代码中自行处理密钥材料的风险。citeturn0search7turn0search8

## 项目定位

一句话定义：

> 面向 `fei.lv` 工具矩阵的统一账户、授权、订阅与集成中心，底层安全能力由 Vault 提供。

### 第一阶段服务对象

- `fei.lv` 及其子域名上的 Web 小工具
- 后续新增的收费工具与 API 产品
- 未来可能支持的私有部署版本

### 不追求的目标

在早期阶段，本项目**不追求**：

- 通用企业级 IAM 平台
- 大而全 OAuth / OIDC Provider 全家桶
- 复杂多租户与组织架构系统
- 过度抽象的插件体系
- 直接让前端访问 Vault
- 把 Vault 当成业务主数据库

## 技术选型

### 后端

- **Go**
- **PostgreSQL**
- **Vault 集成**

后端负责：

- 账号与认证流程
- 会话与 Token 编排
- 应用接入配置
- API Key / License 的业务管理
- 套餐、权限、配额与审计基础
- 对接 Vault 的 transit / pki / secret 能力
- 与 `fei.lv` 工具侧的服务通信

### 前端

- **SvelteKit**

前端负责：

- 管理控制台
- 登录 / 注册 / 应用授权界面
- 账号、套餐、API Key、License 管理页面
- 后期面向用户与管理员的统一控制台

### Rust + WASM（按需引入）

部分对性能或安全更敏感的场景，考虑使用 **Rust WASM**：

- 本地敏感数据预处理
- 特定编码 / 校验逻辑
- 多工具可复用的前端安全模块

原则是：

> 只有在确实带来性能收益、隔离收益或安全收益时，才引入 Rust WASM，而不是为了技术炫耀。

## 与 `fei.lv` 的关系

建议形成如下结构：

- `fei.lv`：流量入口、工具展示、公开页面、SEO 页面
- `*.fei.lv`：不同工具或产品子域名
- `auth.fei.lv`：统一认证与授权入口（由本项目提供）
- `console.fei.lv`：统一用户控制台（后续）
- Vault：建议通过内网或受限安全边界部署，仅服务端访问

这样可以形成清晰分层：

1. **流量层**：免费工具、内容页、场景页、SEO
2. **业务控制层**：统一登录、SSO、订阅、License、应用接入
3. **安全控制层**：Vault 提供 secrets、transit、PKI、审计基础
4. **产品层**：各类独立工具和收费能力

## MVP 边界

### v0.1 必做

- 用户注册 / 登录
- 基础 Session / Token
- 应用模型
- 套餐模型
- Feature Flags 基础
- API Key 元数据管理
- License 基础业务模型
- Vault Transit 集成
- 基础控制台界面

### v0.1 不做

- 完整 OIDC Provider
- 复杂 RBAC
- 多组织协作全家桶
- 全量支付系统
- 直接暴露 Vault 给前端
- 把终端用户体系深度绑定为 Vault 原生登录体系

## 开发原则

1. **优先为 `fei.lv` 自己服务**，不要先做过度通用化
2. **先闭环再抽象**，先服务真实工具接入场景
3. **以商业化支撑为目标**，不是单纯做技术基础设施
4. **Vault 是安全底座，不是业务数据库**
5. **前端不直接访问 Vault，统一通过后端服务编排**

## 近期目标

近期目标不是发布一个复杂平台，而是：

- 支撑 `fei.lv` 工具矩阵的统一登录
- 为收费与高级功能打基础
- 用 Vault 承担签名、密钥与证书相关基础能力
- 为未来 SSO 与私有授权预留明确扩展路径

当 `feilv-auth-center` 能稳定支撑第一批工具接入时，这个项目就已经成功了一半。
