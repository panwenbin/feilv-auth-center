# feilv-auth-center

`feilv-auth-center` 是为 `fei.lv` 及其子域名工具矩阵服务的统一身份、授权、订阅与集成中心。

它的目标不是一开始就做成一个大而全的 IAM 平台，而是优先解决 `fei.lv` 体系内多个工具和产品的共用问题：

- 统一用户账号
- 单点登录（SSO）
- API Key 管理
- 订阅套餐与功能权限
- License / 激活码 / 私有部署授权
- 应用接入与子域名集成
- 为未来的小工具收费、企业版和私有化打底

## 为什么要做这个项目

目前 `fei.lv` 正在通过 Web 小工具持续积累流量。随着工具数量增加，后续会自然遇到这些问题：

- 每个工具重复做登录和用户体系
- 无法统一管理免费版、Pro、Team 等套餐
- 无法为 API、私有部署和桌面/命令行工具提供统一授权能力
- 工具之间账号割裂，用户体验差
- 后期想做 SSO、组织、团队权限时成本很高

`feilv-auth-center` 的定位就是用最小可行方式，把这些基础能力抽出来，形成一个长期可复用的底座。

## 项目定位

一句话定义：

> 面向 `fei.lv` 工具矩阵的统一账号、授权、订阅与集成中心。

### 第一阶段服务对象

- `fei.lv` 及其子域名上的 Web 小工具
- 后续新增的收费工具与 API 产品
- 未来可能支持的私有部署版本

### 不追求的目标

在早期阶段，本项目**不追求**：

- 通用企业级 IAM 平台
- 大而全 OAuth / OIDC Provider 全家桶
- 复杂多租户与组织架构系统
- 过度抽象的插件体系
- 先做一个漂亮但没有业务闭环的后台

## 技术选型

### 后端

- **Go**
- **PostgreSQL**

后端负责：

- 账号与认证
- 会话与 Token
- 应用接入配置
- API Key / License 管理
- 套餐、权限、配额与审计基础
- 与 `fei.lv` 工具侧的服务通信

### 前端

- **SvelteKit**

前端负责：

- 管理控制台
- 登录 / 注册 / 应用授权界面
- 账号、套餐、API Key、License 管理页面
- 后期面向用户与管理员的统一控制台

### Rust + WASM（按需引入）

部分对性能或安全更敏感的场景，考虑使用 **Rust WASM**：

- 密钥相关前端处理
- 本地敏感数据预处理
- 高性能规则校验 / 编码处理
- 前端侧某些可复用安全模块

原则是：

> 只有在确实带来性能收益、隔离收益或安全收益时，才引入 Rust WASM，而不是为了技术炫耀。

## 目标能力地图

### 账号与认证

- 用户注册 / 登录 / 登出
- 邮箱登录与验证
- 密码重置
- Session 管理
- 后续可扩展二步验证

### 应用接入

- 管理多个 `fei.lv` 子域名应用
- 应用级回调地址配置
- SSO 接入配置
- 应用密钥与签名基础

### 授权与权限

- 用户级套餐（Free / Pro / Team）
- Feature Flags
- API Key
- License Key
- 设备 / 域名 / 实例绑定能力基础

### 商业化支持

- 工具按套餐开放功能
- API 调用额度与限制
- 私有部署授权控制
- 企业版后续扩展点

### 审计与可观测性（基础）

- 登录日志
- API Key 使用记录
- License 激活记录
- 关键操作审计基础

## 与 `fei.lv` 的关系

建议形成如下结构：

- `fei.lv`：流量入口、工具展示、公开页面、SEO 页面
- `*.fei.lv`：不同工具或产品子域名
- `auth.fei.lv`：统一认证与授权入口（可作为本项目部署目标之一）
- `console.fei.lv`：统一用户控制台（后续）

这样可以形成清晰分层：

1. **流量层**：免费工具、内容页、场景页、SEO
2. **账号层**：统一登录、SSO、授权、套餐
3. **产品层**：各类独立工具和收费能力

## MVP 边界

### v0.1 必做

- 用户注册 / 登录
- 基础 Session / Token
- 应用模型
- API Key 管理
- 套餐模型
- Feature Flags 基础
- License 基础模型
- 基础控制台界面

### v0.1 不做

- 完整 OIDC Provider
- 复杂 RBAC
- 多组织协作全家桶
- 全面支付系统
- 通知中心
- 完整审计平台
- 插件市场

## 开发原则

1. **优先为 `fei.lv` 自己服务**，不要先做过度通用化
2. **先闭环再抽象**，先服务真实工具接入场景
3. **以商业化支撑为目标**，不是单纯做技术基础设施
4. **最小实现优先**，避免掉进 IAM 黑洞
5. **所有能力都要考虑未来复用**，但不提前过度设计

## 近期目标

近期目标不是发布一个复杂平台，而是：

- 支撑 `fei.lv` 工具矩阵的统一登录
- 为收费与高级功能打基础
- 为未来 SSO 与私有授权预留明确扩展路径

当 `feilv-auth-center` 能稳定支撑第一批工具接入时，这个项目就已经成功了一半。
