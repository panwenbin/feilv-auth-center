# MVP 设计

## 目标

用最小可行方式，支撑 `fei.lv` 工具矩阵的第一批统一账户、授权和商业化能力，并让 Vault 承担底层签名、密钥和部分证书相关能力。

MVP 的目标不是完美，而是尽快完成第一个真实闭环：

- 用户可以注册登录
- 工具可以接入统一认证
- 不同套餐可以控制功能开放
- 可以管理 API Key 或 License
- Vault 已真实承担至少一种安全能力

## MVP 范围

### 1. 用户与认证

- 邮箱注册
- 邮箱登录
- 登出
- 重置密码
- 邮箱验证（可延后到 v0.2，但建议预留模型）
- Session 管理

### 2. 应用接入

- 创建应用
- 为应用分配唯一标识
- 配置回调地址 / 来源域名
- 应用基础密钥元数据

### 3. SSO 基础

- 用户登录后可在多个接入应用间复用登录态
- 提供基础票据 / token 校验机制
- 明确后续升级到更标准协议的路径

### 4. 套餐与功能开关

- Free / Pro / Team 三层基础模型
- Feature Flags
- 用户与套餐绑定
- 工具侧根据能力标识判断是否开放功能

### 5. API Key

- 创建 API Key
- 查看与禁用 API Key
- 记录创建时间、最后使用时间、权限范围基础字段
- 原始敏感材料不在业务层长期明文保存

### 6. License 基础

- 生成 License 业务对象
- 绑定用户 / 套餐 / 产品
- 支持到期时间
- 为未来实例激活 / 域名绑定预留字段

### 7. Vault 集成基础

- Vault client 封装
- Transit key 初始化
- 基础签名 / 验签能力
- 为 License、票据或应用签名提供安全底座

### 8. 基础控制台

- 登录页
- 用户资料页
- 我的应用（可简化为后台管理）
- 我的 API Key
- 我的 License
- 我的订阅 / 套餐展示

## 明确不做

以下能力容易让项目失控，MVP 阶段不做：

- 完整 OAuth2 / OIDC 兼容矩阵
- 企业级 RBAC
- 多组织 / 多团队协作全套
- 全支付流程集成
- 复杂审计检索系统
- 通知中心
- 登录方式大全（短信、GitHub、微信、魔法链接等）
- 让前端直接访问 Vault
- 在 MVP 阶段深度耦合 Vault Identity / 多 auth methods / PKI 全流程

## MVP 角色模型

### 普通用户

- 注册登录
- 查看和管理自己的 API Key / License / 套餐

### 管理员

- 管理应用
- 管理用户套餐
- 生成和管理 License
- 查看基础操作日志
- 管理与 Vault 相关的基础配置映射（必要时）

## MVP 成功标准

当以下闭环可用时，可以认为 MVP 达标：

1. 某个 `fei.lv` 工具接入统一登录
2. 该工具的高级功能可根据套餐控制
3. 用户能在中心创建 API Key 或获得 License
4. 管理后台可完成最基础的应用与授权管理
5. Vault Transit 已被真实用于至少一种签名 / 验签场景

## 建议接入顺序

### 第一批接入对象

优先接入最接近商业化的工具，而不是最复杂的工具。

推荐优先接入：

1. 开发者 / 站长工具
2. 未来准备增加高级功能的工具
3. 后续可能有 API 能力的工具

### 不建议首批接入

- 访问量很小且短期不收费的边缘工具
- 逻辑过于特殊的实验性工具
- 需要复杂 PKI 场景才能落地的工具

## MVP 数据对象建议

至少需要这些核心对象：

- users
- user_credentials
- sessions
- applications
- application_domains
- plans
- features
- plan_features
- user_subscriptions
- api_keys
- licenses
- audit_logs

此外应定义与 Vault 集成有关的配置边界，但 Vault 中的 secret / key material 不作为业务数据库对象直接建模。

## 技术实现建议

### 后端

- Go 单体优先
- PostgreSQL 作为业务主存储
- Vault 作为安全能力底座
- 清晰模块边界优先于微服务拆分

### 前端

- SvelteKit 管理控制台
- SSR + 表单优先，减少前期复杂前端状态管理
- 通过后端 API 间接使用 Vault 相关能力

### Rust WASM

MVP 阶段只在明确需要时引入，例如：

- 敏感数据本地预处理
- 特定签名 / 编码辅助逻辑

如果没有明显收益，不建议在 v0.1 就引入过多 Rust WASM 复杂度。

## 版本节奏建议

- v0.1：用户 / 应用 / 套餐 / API Key / License 基础闭环 + Vault Transit 集成
- v0.2：SSO 强化、邮件验证、审计增强、必要的 Vault 能力扩展
- v0.3：支付集成、更多工具接入、私有部署授权扩展、PKI 场景落地
