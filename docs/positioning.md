# 项目定位

## 核心定位

`feilv-auth-center` 是 `fei.lv` 工具矩阵的统一账户、授权、订阅与集成中心；**Vault 作为底层安全能力支撑**。

它首先是一个**为真实业务服务的控制面**，其次才可能成长为一个更可复用的平台。

## 为什么引入 Vault

引入 Vault 的目的，不是把终端用户产品逻辑全部搬进去，而是把以下底层安全能力交给成熟组件：

- 密钥管理
- 签名 / 验签 / HMAC
- 敏感数据加解密
- PKI / 证书生命周期
- 机器身份与部分 auth methods
- 安全审计基础

Vault 支持多种 auth methods，并在认证后发放 token 和 policies；其 identity 模型可以用 entity 和 alias 统一不同身份源的表示。citeturn0search0turn0search1turn0search3

Vault 的 transit 引擎可以承担签名、验签、HMAC 和加解密等敏感操作，这适合用来支撑 License、票据、应用签名等场景。citeturn0search7turn0search8

## 解决的问题

随着 `fei.lv` 上的免费工具、收费工具、API 工具和私有部署工具逐步增加，会持续出现以下问题：

1. 账号体系重复建设
2. 各工具权限规则不一致
3. 订阅套餐无法统一管理
4. API Key、License、实例授权难以统一
5. 工具之间缺乏单点登录能力
6. 密钥、证书和签名逻辑如果分散在各工具中，安全与维护成本过高

`feilv-auth-center` 就是用来把这些业务问题收敛到一个统一中心，并把安全底座建立在 Vault 上。

## 目标用户

### 第一层：内部用户

- `fei.lv` 体系下的各工具与子产品
- 管理后台
- API 服务和私有部署实例

### 第二层：最终用户

- 使用 `fei.lv` 免费工具的普通用户
- 购买高级功能的 Pro 用户
- 使用多个工具的重度用户
- 未来可能的团队 / 企业客户

## 核心价值

### 对用户

- 一个账号通行多个工具
- 更清晰的权限、授权与套餐体验
- 可统一管理 API Key、License、订阅与历史记录

### 对产品

- 不再重复做登录、权限、授权、套餐逻辑
- 更容易推出收费功能
- 更容易接入签名、证书、授权等安全能力

### 对业务

- 让流量资产沉淀成用户资产
- 让用户资产进一步转化为订阅与授权收入
- 让未来的企业版和私有化更容易实现

## 控制面与安全面的边界

### `feilv-auth-center` 负责

- 用户产品账户
- 应用接入
- 套餐与 Feature
- API Key / License 的业务模型
- SSO 流程编排
- 控制台与商业化流程

### Vault 负责

- Secrets 管理
- Transit crypto 能力
- PKI / 证书
- 机器身份与部分认证方法
- 安全审计基础

### 不应该做的事情

- 不把 Vault 当成业务主数据库
- 不让前端直接访问 Vault
- 不让产品套餐模型直接等同于 Vault policy
- 不在 MVP 阶段把终端用户登录完全绑定到 Vault 原生 auth method

## 项目成功标准

如果在早期阶段满足以下条件，就说明方向是对的：

1. `fei.lv` 第一批工具已经接入统一登录
2. 至少有一类高级功能通过套餐 / 授权控制实现收费
3. 用户能统一管理 API Key 或 License
4. Vault 已被真实用于签名、密钥或证书相关场景
5. 新工具接入账号体系和安全能力的开发成本明显降低

## 长期演进方向

### 近阶段

- 成为 `fei.lv` 的账户和商业化控制中心
- 形成与 Vault 的稳定安全集成层

### 中阶段

- 成为多工具共享的 SSO / 授权中心
- 增强 License、私有部署与证书相关场景

### 远阶段

- 在真实业务打磨成熟后，选择性开放为独立产品或私有部署能力

## 设计原则

1. 先解决真实问题，再做抽象
2. 先保证接入简单，再追求完美架构
3. Vault 用来承载安全原语，不替代业务控制面
4. 所有新能力都必须说明服务哪个真实场景
5. 没有明确接入方的能力，不优先开发
